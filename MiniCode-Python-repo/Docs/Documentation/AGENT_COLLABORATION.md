# 子代理持续协作

本次改进支持主代理围绕同一模块反复派工、子代理直接讨论接口，以及可恢复的结果通知。新建且已启用异步代理消息的运行默认启用；历史运行继续使用其持久化策略，不在恢复时自动增加权限。

## 工作方式

主代理通过 `spawn_agents` 指定名称、目标、文件范围、验收要求和可选局部检查。子代理完成后，运行时在主代理下一次模型或工具边界投递完成摘要，附上结果位置、退出状态、局部检查和版本信息。主代理检查证据后，通过 `ack_agent_results` 记录处理情况，再决定继续派工或进行集成验收。

相关后续任务用 `resume_agent` 分配给原会话。`session_id` 和名称保持稳定，新任务获得新的 `task_id` 和递增的 `generation`。保留此前的对话、消息和检查结果；每次重新读取当前文件，旧的文件读取凭据不授予下一轮写入权限。写代理必须重新提供非空 `write_scope`，可以重新指定 `acceptance_criteria` 和 `checks`。

正在运行的子代理可以通过 `interrupt_agent` 中断。部分文件修改与最后一个安全边界的上下文会保留。仅在原工作进程确实退出、没有未确定的副作用后，才允许新一轮继续执行。中断本身不使原任务成功：原节点仍保留取消记录，只有继任任务通过验证，才能解除对应的完成阻塞。中断前的验收要求会继承。普通 `cancel_agent`、后续再次取消、运行整体取消和失败任务均不能通过此入口绕过。

辅助调查确实可以省略时，在首次 `spawn_agents` 的任务中显式指定 `optional: true`，仅支持 `explore`、`plan`、`review`。默认所有任务仍是必需任务；写入助手和独立核验助手不能设为可选。同一任务的重试、会话续接和失败接替不能改变这个约定。

`cancel_agent` 只停止执行。可选任务取消或失败后，主代理确认不再需要其结果，可以调用 `dismiss_agent(task_id, operation_id, reason)` 明确解除交付要求。已启动的工作必须有实际退出记录，未确定的副作用不能通过该入口忽略；从未启动的任务不需要虚构退出记录。取消或失败状态、费用、证据和放弃理由均保留，放弃不算成功、结果处理或验收。目录和查询回执提供 `optional`、`dismissed` 及当前是否允许放弃的状态。该决定同时约束最终验收和团队收尾，恢复运行后继续有效。

放弃旧轮次不会停止已经登记的后续工作，后续任务仍需完成或单独处理。已经放弃的任务不能再派生新的续接。普通取消撤销中断续接关系后，旧轮次仍保留独立的交付要求；只有它本来就是可选任务时，才能另外明确放弃。

## 余额不足后的跨轮续接

供应商明确拒绝余额/计费时，运行时记录 `ProviderBalanceUnavailable`，停止后续模型请求，不把它当成普通工具失败自动重试或切换模型。已执行的工具结果和上下文检查点保留；正在执行的工具批次先收尾，用户主动停止仍立即生效。重启旧运行不会清除计费熔断，用户补充余额后通过新的会话轮次继续。

新一轮启用子代理续接时，`list_agents` 的 `retained_agents` 返回同一会话、同一工作区上一轮的团队和结果。主代理先复用已完成成果，对相关未完成工作调用 `resume_agent`，传入旧 `task_id` 和本轮目标。新任务保留原 `session_id`、名称、上下文和递增轮次，获得新的 `task_id`、工作区绑定和权限。写代理重新提供 `write_scope`，继承原验收要求，重新读取当前文件。原始运行状态和费用账本不修改，本轮仍受当前预算约束。

恢复前取得旧运行的排他锁并验证持久化状态、真实退出记录、检查点归属和完整性。用户整体取消、单独取消、未退出进程、不确定副作用、缺失/损坏检查点、独立核验代理、达到会话轮次上限，以及依赖旧隔离候选的写代理均不能直接续接；目录提供 `blocked_reason`。旧工具调用、读文件凭据、检查通过记录和审批不重放、不授予本轮权限。无法续接时，主代理应先核对保留下来的文件与结果，再分配接替工作。

这个入口只提供紧邻上一轮因余额中断的团队，不自动启动任何历史任务，也不跨聊天搜索代理。前端使用持久化恢复关系把旧轮和新轮归到同一个子代理，余额停止显示“余额不足 · 等待继续”。

## 独立上下文与交接笔记

每个子代理拥有自己的消息列表、短期工作记忆、上下文管理器及整理记录。派工可提供用户约束、任务背景或显式 fork 的历史，但这些内容进入子代理的独立副本；之后追加消息和整理上下文不会修改主代理或兄弟代理的消息列表。共享工作区中的项目文件仍然是共享的，运行的 Token、费用和时间总额度也仍然统一约束各代理。

新建子代理不继承主代理 `_sessionContextState` 中的临时工作记忆或整理级别。原生上下文检查点按任务节点保存消息、工作记忆和整理记录；恢复时加载该子代理的检查点，即使调用方没有提供 `ContextManager`，也会创建并恢复自己的管理器。`resume_agent` 续接保留对话和整理记录，同时重置旧轮次的短期执行凭据；旧的文件读取记录、任务范围和笔记不能替代新任务的授权或文件核对。

启用分页记忆及交接配置（`memoryV2`、`memoryHandoffNotesEnabled`、`memoryContextRotationEnabled`）后，子代理可使用与主代理相同的 `memory_note_update` 和 `context_rotate`。运行配置继续决定实际启用状态；本次修复不会修改已有配置。每个子代理创建自己的分页记忆运行实例，沿用任务的存储配置，但不复用主代理已经绑定身份的实例。

交接笔记包含四类内容：已确认发现、已排除方案、待解决问题和下一步行动。前两类必须引用可核验的原始事件；笔记更新需要匹配版本，整理需要匹配上下文轮次和笔记版本。笔记归属由运行时绑定到对应代理，不能由模型参数任意指定。只读子代理也可更新自己的笔记和整理自己的上下文，这不会授予项目文件写入权限。

笔记和整理记录持久化到关系型存储；恢复时校验归属、来源、用户要求和任务约束。任务范围或要求变化后，旧笔记不能直接视为当前结论，需要重新核对。模型撰写的笔记是工作参考，不能覆盖用户要求，也不能代替真实源文件、测试结果和最终验收。程序验证隔离、存储和恢复机制，不保证模型每次都能完整概括所有细节。

## 直接通信

子代理可用 `list_agents` 查询同一运行中的成员和当前任务，用 `send_agent_message` 向同一主代理下的其他子代理发送问题、进度或结果。独立核验代理不开放这两个工具，也不接受主代理或兄弟代理发送的追加消息；任务与验收要求在初次派工时提供。目录中的可通信状态和实际发送使用同一条路由规则。直接交流不会转移文件所有权、扩大修改范围或授权新任务。

- 使用 `session_id` 寻址会解析到当前轮；使用后续轮的 `task_id` 可准确指向该轮。
- `reply_to` 使用收到的原消息标识 `sender_id:message_id`。原消息必须已进入接收方持久化上下文。
- 同一发送方重复提交相同 `message_id`，返回原投递记录；即使会话已有下一轮，也不会重新投递到新轮。
- `queued` 表示已排队，`consumed` 表示进入持久化上下文，均不代表对方已经完成工作。
- 已完成、取消或正在封闭提交的任务不会因为收到消息自动开始工作；需要主代理显式续接。
- 目录默认每页返回最多 32 个当前成员；`include_history=true` 可查看以前的任务轮次。

## 局部检查与最终验收

主代理在任务的 `checks` 中声明检查，例如：

```json
{
  "id": "simulation",
  "command": "python",
  "args": ["-m", "pytest", "tests/test_simulation.py"],
  "cwd": ".",
  "timeout_seconds": 120
}
```

子代理只能用 `run_agent_check(check_id, operation_id)` 执行本轮已声明的检查，不能在调用时换成任意命令。默认直接在当前共享工作目录执行，与主代理最终核验遵守同一个 `runtimeVerificationIsolation` 配置：未配置、`null` 或 `false` 均不创建副本；只有显式设为 `true` 才使用独立文件副本。返回退出码、输入版本、源文件是否仍与检查前一致、实际工作区模式、耗时和报告文件。正常命令权限、超时和取消规则继续生效。

直接执行时，临时输出和缓存使用 `.temp/verification/check-*`，可通过 `MINICODE_VERIFICATION_OUTPUT_DIR` 写入报告；实际文件修改会保留。检查期间源文件变化会使本次检查失败，不会自动回滚或改用副本。主代理应协调共享写入与检查顺序，并在所有写入助手退出后进行最终集成检查。原生文件工具的 `write_scope` 不构成子进程的文件系统沙箱，声明命令仍须经过现有权限机制。局部检查通过不能代替主任务对最终组合文件的构建、测试和独立核验。

每个任务最多声明 8 个检查，每个检查最长 300 秒，每轮最多执行 32 次。重复 `operation_id` 只读取原结果。进程丢失后尚未结束的检查保留未完成状态，不自动重放或宣称通过；确需重试时明确使用新标识。

完成通知、`ack_agent_results` 和局部检查回执都带有“不作为最终验收”的语义。尚未送入主代理上下文的通知不能提前确认处理，也不能被主代理直接提交候选结果绕过。已处理的旧轮次从每次请求的活动摘要中移出，完整历史仍保留。

每次模型请求的原生任务摘要（含提示文字）最多 32 KiB。详情超限时优先保留正在执行和仍阻塞交付的任务，展示未解决任务总数、未处理结果数和各类省略数量。用 `list_agents(include_history=true, cursor=0)` 按 `next_cursor` 翻页，再用 `poll_agents(task_ids=[...])` 读取指定结果。摘要压缩不会确认处理、删除任务或解除交付要求；已经恢复执行的旧等待只保留计数，不重复携带完整依赖边，原始等待事件仍在持久化记录中。

## 配置与额度

以下为支持的配置字段。它们不改变整个运行的时间、Token、费用和权限限制。

| 配置 | 默认值 | 含义 |
| --- | --- | --- |
| `runtimeAgentCollaboration` | 随异步消息能力启用 | 新运行是否使用持续协作策略 |
| `runtimeAgentPeerMessages` | `true` | 是否允许同主代理下的兄弟通信 |
| `runtimeAgentMaxGenerations` | 16 | 单个稳定会话的最大轮次，上限 128 |
| `runtimeAgentMaxSessions` | 8 | 活跃会话数上限，上限 64；退役需启用原有团队控制 |
| `runtimeAgentMaxTasks` | 至少 64 | 累计任务节点数，含主任务与核验节点，上限 512 |
| `runtimeAgentMaxMessages` | 1024 | 本次运行累计消息数，上限 16384 |
| `runtimeAgentMaxPendingMessages` | 32 | 单个接收任务待消费消息数，上限 128 |

新策略中的 `runtimeMaxAgents` 限制不同逻辑会话与其他任务节点之和，继续原会话不会每轮重复占用该额度。例如主任务、最终核验和一个持续工作的子代理可以只占 3 个名额。任务总数仍受 `runtimeAgentMaxTasks` 限制。退役和消费消息都不会重置累计额度。

`runtimeMaxActiveWorkers`、`runtimeMaxActiveWriters` 继续限制真实并发；`runtimeMaxContinuations` 继续限制主代理恢复次数。提高某一项不会放宽其他额度，较长任务需要按实际工作量协调设置。消息总量耗尽与接收方积压分别报错，等待接收方消费只能缓解积压。

旧运行保留原有轮次、消息和派工限制。协作策略随状态版本 `minicode-runtime-state-v20` 持久化，完成与处理回执、检查凭据、中断请求和可选任务放弃记录均有对应原生事件。历史状态不通过修改版本字段获取新能力；缺少 `optional` 的旧任务按必需任务处理。

## 界面

子代理列表与通信记录使用持久化名称；同一会话的各轮任务归在一起。详情展示轮次、已记录的实际模型、任务范围、验收要求、局部检查和结果处理情况。显示“本轮完成 · 可继续接任务”或“已中断 · 可继续任务”时，表示当前运行具备续接条件，实际调用仍会重新检查状态、工作进程退出和额度。

端到端测试使用本地确定性模型协议服务，文件修改、进程、调度、持久化和验收均运行真实实现；它不评估真实模型自主选择协作策略的质量。余额恢复专项位于 `tests/test_agent_balance_recovery.py`，覆盖真实 HTTP 402、部分写入保留、跨轮/进程续接、轮转笔记的独立归属、拒绝不安全恢复，以及生产调度器从余额中断到续接和最终检查的完整链路。任意历史运行的长期复用、递归委派和自动模型选型未纳入本次改进。

子代理执行中的 Python 异常会转换为任务失败与退出记录。子线程的 `SystemExit`、`KeyboardInterrupt` 不应传到主调度器；真实主线程 Ctrl+C、全局停止和预算限制仍然有效。子任务启动前上下文失败同样会通知主代理。单任务取消保持独立，不自动取消父任务或无关兄弟任务。

共享写入后异常退出的任务保留部分修改，并通过不确定副作用记录阻止未经核对的重试或交付。中断后续接完成的团队成员，按原尝试的真实退出记录和后继任务的成功状态收尾。线程隔离无法覆盖整个 Python 进程被终止或原生扩展使进程崩溃的情况。

整体取消或预算停止后，调度器只在取消宽限期内等待 Worker 收尾。仍有执行未退出时，运行返回未完成结果，并在调度报告 `unsettled_task_ids`（Web 投影为 `unsettledTaskIds`）中列出清理待完成的任务。此时不启动最终检查，也不读取最终输出作为验收证据；取消状态不充当真实退出凭据。

调度器自身抛错时，也会先记录整次运行取消，再将原异常交还调用方，防止迟到的成功结果被接收。若取消状态持久化失败，保留原异常并记录该失败；运行锁仍按实际执行的退出情况交接。

返回调用方后，原运行继续持有工作区写锁、运行状态锁和未退出 Worker 的并发占用。其他运行不能接管同一工作区或状态文件；迟到结果只用于收尾与实际用量结算，不使已取消任务成功，也不会自动重放。所有未退出执行及其回执处理结束后才释放运行锁。报告是返回时的快照，后续退出以持久化的 Worker 记录为准。并发安全的只读工具收到取消后及时返回取消回执，不再等待原工具超时。

这项优化保留共享工作目录，不创建文件副本，不强杀 Python 线程，也不回滚真实修改。底层调用若永不返回，对应占用仍保持；需要终止宿主进程或另行引入可强制终止的受控子进程，才能处理这一剩余边界。取消与锁交接通过 `tests/test_runtime_shutdown.py` 的真实文件写入、阻塞调用、跨进程锁探测及完整 HTTP 协议链路验证；只读取消通过 `tests/test_tool_cancellation.py` 验证。
